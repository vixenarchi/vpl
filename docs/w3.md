# w3 — a site from a description

*Proposed, not built. Written so that the first slice can be argued about before it
is code.*

`terg.hr` is hand-written HTML in a folder that is not in this repository. It
should be generated, by us, with the same engine the other eight use — and then
it should be possible for a person who is not us to generate their own.

That is the whole of `w3`: **one description in, one site out, no editor to learn.**

## The one sentence

> A site is a title, a few pages of text, and the order they are read in.

Everything else a site generator usually grows — themes, blocks, layouts, menus,
revisions, plugins, a page builder with a canvas — is an answer to a question
nobody asked. Our sites are prose. Prose needs a title per page and an order.

## Three surfaces, one list

Same shape as the rest of the suite: a rail, a work column, and nothing else.

- **the list** — sites. One row: title, how many pages, published or not.
- **the page** — one site: its pages in reading order, each a title and a body.
  The body is plain text (markdown), typed in the same editor `vn` uses, with the
  same paste rule (a paste is cleaned at the door).
- **the sheet** — what a visitor would see, rendered by the same markdown path
  and the same `tokens.css`. If the sheet and the page disagree, the sheet wins,
  because it is the only one a stranger ever sees.

There is no fourth surface. A site that needs a fourth surface is a website
builder, and we are not building one.

## What the model does, and what it does not

The engine (`packages/shell/engine.js`, copied in, never imported) gets the
description *and* the current pages, and returns **pages** — never HTML, never CSS,
never a layout. The grammar is the same one `vc` uses: a closed, boring line
format, so a partial answer is visible as a partial answer.

```
## <page title>
<prose>
```

And the rules that already hold everywhere:

- **the balloon rule** — the model proposes in a speech balloon; a person presses
  *use it* or *drop*. Nothing a model writes lands in a field on its own.
- **a change is answered with the changed text only** — "make the pricing page
  shorter" returns that page, not the site.
- **the model may not delete a page.** It may propose a page as struck out; a
  person deletes.
- **one credit is one call** — a site is one call if it fits, and a site that does
  not fit is a site to shorten, not a job to queue. `w3` has no batch. (`vc` owns
  the queue; a second queue is a second failure mode.)

## The data model — deliberately poor

Two tables, prefix `w3_`:

- `w3_sites` — `id`, `user_id`, `title`, `slug`, `summary`, `published_at`,
  `deleted_at`, timestamps.
- `w3_pages` — `id`, `site_id`, `user_id`, `title`, `body`, `pos`, `deleted_at`,
  timestamps. A page is a row; the order is `pos`, the same integer the rest of the
  suite uses.

No blocks, no nodes, no tree. A page has a body and a number. Publishing is
`published_at` on the site — a switch, not a second table, and not a build step.

## Publishing is a copy, not a pointer

A published site is written out as **files** — `index.html` plus one file per
page — through the same door `vd` and `vc` use. The published copy never reads the
database at request time: if we stop paying, the site keeps answering. That is the
same rule as `vc`'s *a copy, not a pointer*, applied to HTML.

Where it lands is a second decision, and it is not this app's: `w3` writes files
and says where they went. Wiring a domain is a dashboard step, exactly as it is
for the eight apps.

## What is deliberately not built

- **No canvas, no drag-to-arrange, no live preview beside the editor.** The
  sheet is one press away and it is the whole screen, because a half-size preview
  teaches you to trust a lie.
- **No themes.** One design, from `tokens.css`, which is the design the suite
  already has. A site builder whose first feature is a theme picker is a template
  shop.
- **No images in slice one.** An image needs a host, a size, alt text and a
  decision about who may look at it; that is a slice, not an afterthought.
- **No comments, no analytics, no forms, no SEO knobs.** A site is text.
- **No navigation editor.** The order of the pages *is* the navigation.

## Slice plan

1. **the list and the page** — a site, its pages, in order, typed and saved. No
   model, no publish. `w3-check.mjs` in `apps/vn/test`, one bin, one guest view.
2. **the sheet** — render a site as a visitor sees it, with the print rule
   (`chrome does not print`) already satisfied.
3. **the model** — one call, the balloon, *use it* / *drop*, the closed grammar.
4. **publish** — files out through the door, `published_at` a switch, a copy that
   survives us.
5. **the first real site** — `terg.hr`, generated by `w3`, replacing the folder
   that is not in this repository. If the output is worse than the hand-written
   pages, the last slice is a failure and should be said so.

## Three questions for the person who owns the suite

1. **Whose site is it?** One `w3` for us only (a private tool, no guest, no
   sharing) — or the ninth app in the suite, with the same sign-in, sharing and
   bin? The first is a week, the second is three and it earns a subdomain.
2. **Does a stranger ever edit their own site here?** If yes, `slug` and
   publishing become public surface and step 1 needs a claim on names, like a
   mailbox. If no, a site is only ever ours and `slug` is ours.
3. **Does `terg.hr` itself move onto `w3` in this project, or does `w3` only get
   used for the sites after it?** Moving our own front door onto a four-day-old
   generator is a real risk and it should be a choice, not a side effect.
